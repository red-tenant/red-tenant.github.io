    Red Tenant Project for Active Directory¶

    The Red Tenant Project for Active Directory is the home for all the thought on using an Entra ID "red tenant" to protect Tier 0 resources, like Domain Administrators, in Active Directory.

    These notes are an evolved Notion, but still relatively young.

    Get Involved¶

    If you have interest in helping flesh out the ideas for a red tenant, automating components, contributing research, and so on, we'd love to hear them! Reach out to us at:

    Warning¶

    As Red Tenant is still an architectural concept, proceed with caution in a production environment.

    Terminology¶

    Because we are deploying an architecture that is new, there is some new terminology that would generally not be used. For purposes of this project we will use the following:

    Red tenant¶

    This is the tenant that will be used as the red tenant. The red tenant is for Tier 0.

    Red tenant Entra Connect¶

    This is the Entra Connect used for the red tenant for Tier 0 user synchronization.

    Enterprise tenant¶

    This is the "production" tenant that would already exist in a shop that consumes Microsoft 365 and/or Azure services

    Enterprise Active Directory¶

    This is the "production" Active Directory

    Enterprise Entra Connect¶

    This is the "production" Entra Connect

    Prerequisites¶

    To build a red tenant you will need:

    • An Entra tenant as the "red tenant"
    • An Active Directory forest
    • An Entra connect server for red tenant sync
    • Active Directory Certificate Services integrated into Active Directory
    • A PAW (could be virtualized for lab purposes)

    To fully replicate an enterprise architecture for an organization using Microsoft 365 services:

    • A second Entra tenant that is the connected to Active Directory
    • A second Entra connect server that is connected to Active Directory

    To fully replicate the Azure subscription architecture:

    • An Azure subscription associated with the red tenant

    To fully replicate the Azure subscription architecture with networking:

    • A second cloud, Azure subscription associated with another tenant, or on-prem site for site-to-site (S2S) networking

    Assumptions¶

    For testing a red tenant there are some presumptions made:

    • You have some familiarity with consuming Microsoft 365 services, Entra ID, and Active Directory.
    • You have a willingness to learn and explore.

    While we will provide links to Microsoft docs, we cannot provide end-to-end details on every step.

    However, if documentation is not clear, please open an Issue in GitHub.

    There are also technical assumptions:

    • Active Directory is built using a FQDN that you own and have control over, necessary for Entra Connect sync, or you are comfortable using an onmicrosoft.com domain. Note Microsoft applies some limits in M365 to tenants that do not have a custom domain installed.
    • Control over the domain name(s) being used for DNS purposes.
    • Enterprise Entra Connect tier 0 users are excluded from synchronization
    • There is no red forest
    • AD CS functions and can issue necessary certs to Domain Controllers
    • Windows Hello for Business Cloud Kerberos Trust is used for Enterprise Active Directory
      • There should not be an issue if Key Trust is used instead for Enterprise Active Directory

    Deployment¶

    The following is the overview of what a Red Tenant deployment would look like. Some of these steps are dependent on the last, so the order matters.

    1. Entra Red Tenant¶

    You will need an Entra ID tenant, preferably with M365 E5 or EMS E5 licensing.

    Entra ID Premium 2 licensing will not provide all the MDM controls if you want to test them from an Intune-managed PAW perspective.

    While Microsoft has limited the availability, if you have a Visual Studio subscription or meet other requirements you can obtain a tenant using the M365 Developer Program.

    If you work for a Microsoft partner, you may have access to Microsoft Demo eXperiences (MDX) for an Entra tenant. MDX was formerly known as demos.microsoft.com and/or the CDX portal.

    Add a custom domain following these instructions, Add a domain to Microsoft 365.

    2. Active Directory¶

    Ensure that your Tier 0 and privileged users exist in an OU structure that can be targeted by Entra Connect. A flat or nested OU structure is fine, but device objects and groups should be excluded.

    Add the custom domain you configured for your red tenant in Active Directory as an alternate UPN suffix. While these docs are for resolving a non-routeable domain, they also work for this purpose, Add UPN suffixes and update your users to them.

    3. Red tenant Entra Connect¶

    Deploy a Windows Server 2022 VM or later in Azure. Microsoft doesn't explicitly state that Server 2025 isn't supported, however, they still recommend Server 2022. Upon deployment, you should ensure that the extension is installed to allow sign-in with Entra ID. Full details of how this functions can be found here, Sign in to Windows virtual machine in Azure or Arc-enabled Windows Server, using Microsoft Entra ID and Azure Roles Based Access Control.

    The server will need DNS name servers set that can resolve hostnames in the Enterprise Active Directory domain.

    Sign in to the server with an Entra ID account that has administrative rights on the VM. This user does not have to be a Global Administrator.

    We will be using a custom installation of Microsoft Entra Connect, the full docs are here, Custom installation of Microsoft Entra Connect.

    1. For User sign-in, select Password Hash Synchronization. Do not enable single sign-on (the name is misleading). Select next.
    2. Authenticate to your red tenant using a Hybrid Identity Administrator (least privilege) or Global Administrator (high privileged).
    3. Connect to the Enterprise Active Directory domain. Ensure you enter the FQDN of the Active Directory domain, and make sure you select create new account. Select next.
    4. For Entra Connect sign-in configuration, make sure that the UPN suffix for your red tenant is marked as Verified. There will be a note that your prod domain is not verified, this is expected and ok.
    5. Leave the User principal name matching set to userPrincipalName.
    6. Check the box for Continue without matching all UPN suffixes to verified domains. Select next.
    7. For Domain and OU filtering, select Sync selected domains and OUs, uncheck the root of the domain, and then expand out and find only the OU that you want to sync for your privileged users. Select next.
    8. Do not change any settings for uniquely identifying your users. Select next.
    9. Do not set a sync filter based on groups. Select next.
    10. Do not set any of the optional settings. Select next.
    11. Select Start the synchronization process as soon as the configuration completes. Select Install.

    After the installation completes, Entra Connect will synchronize your Domain Admins out to your red tenant.

    4. Red Tenant Windows Hello for Business¶

    We need to run through a Windows Hello for Business (WHfB) hybrid key trust deployment.

    Note that while the WHfB deployment is hybrid key trust, the devices (PAW) that will be used do not need to be, and should not be, hybrid joined.

    One key item to point out during deployment is needing to ensure that the CRL CDP is published to an http endpoint. This is in the docs, but it is the only method available to Entra-joined Windows clients for checking the CRL.

    There are PKI scenarios that call for publishing the CRL endpoint to the internet, and Microsoft documentation that explains how to do so with Entra App proxy. For purposes of WHfB, the CRL is only important when authenticating against Active Directory, so as long as you have line-of-sight of the CRL endpoint when you also have line-of-sight of Active Directory, that will suffice.

    Hybrid key trust deployment guide Configure single sign-on for Microsoft Entra joined devices

    It's also important to deploy the Nondestructive PIN reset service. This limits credential rotation needs and playing with AdminSDHolder as noted under msDS-KeyCredentialLink. Dos for deploying this service are found here, PIN reset.
